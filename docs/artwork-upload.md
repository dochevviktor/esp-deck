# Direct artwork uploads

The 2026-10-12 change makes native API uploads the default for HA library artwork
when the firmware advertises `artwork_upload: png_chunks_v1`. HA already owns the
normalized 72×72 PNG and an encrypted ESPHome connection. Sending those bytes on
that connection removes the need for an ESP-to-HA HTTP route, an artwork server
address, and download tokens in the normal editing flow.

Install the updated HA integration and compatible example-05 firmware to use it.
The owner-requested update is now deployed to the physical ESP and HA; real
upload/decode/render/USB completion and cached state redraws passed with zero
HTTP downloads. [Physical session and remaining gates](hardware-lab.md).
Existing saved artwork hashes and layouts need no migration. Older v1/v2 firmware
continues using the restricted HTTP route; explicitly configured external image
URLs still use the original allowlist/TLS/fetch limits. Origin provisioning is
an advanced HTTP option. Neither path rasterizes dynamic labels in HA.

## API and lifecycle

An optional new response action, `upload_deck_artwork`, takes fixed arguments:

| Argument | Meaning |
| --- | --- |
| `session` | Current 16-character ESP boot session |
| `asset_id` | Lowercase 64-character SHA-256 of the complete normalized PNG |
| `offset` | Decoded byte offset, starting at zero |
| `total_size` | File size in bytes, 1–32768 |
| `data` | Strict base64 of at most 1024 decoded bytes (1368 encoded characters) |

Responses contain `session`, `accepted`, `error`, `received` and `complete`.
An empty chunk at offset zero probes the cache or begins/resumes reception.
HA waits for every acknowledgement before sending the next chunk. Exact duplicate
chunks are idempotent; conflicting, skipped, oversized and malformed chunks are
rejected. A different asset beginning at offset zero replaces the incomplete
transfer. Only one incomplete transfer exists, expiring after 15 seconds without
progress or 60 seconds total. Duplicate probes/chunks do not extend these limits.
All incoming messages are well below the pinned ESP32 native API's 32 KiB cap.

`complete: true` means the full file passed SHA-256 verification and the 72×72,
non-interlaced PNG header gate and entered the immutable source cache. It is not
a claim of PNG decoding or display completion. The existing bounded PNG decoder
checks CRCs, chunks and compressed content during rendering. Malformed content
retains the previous tile and reports the existing visual error status.

After completion, HA submits the normal `set_key_visual_v2` action with
`image_url: asset://<sha256>` and `image_revision: <sha256>`. This reserved local
reference is accepted only by v2 and requires the revision to match its hash.
It never reaches HTTP. v1 signatures and HTTP URL validation remain unchanged.
The reference is generated by the backend; persisted layouts still contain only
`asset_id` hashes. Users do not enter offsets, hashes or internal references.

Transfers alone cannot change the display or key binding context. The normal
Store/revision/input fences and two-page USB scheduler still govern application.
HA drops work when the layout changes during transfer. Stale render completions
cannot commit. Page 1 and page 2 retain the same immutable native image.
USB-applied status remains host completion, not physical display readback.

## Memory and reuse

The upload cache holds at most sixteen immutable compressed PNGs plus one
receiving buffer: at most 557,056 bytes of payload. All allocations share the
existing 2 MiB graphics budget and use PSRAM on the ESP. Allocation failure is
reported without replacing a displayed image. The fifteen desired keys pin their
source files; unreferenced entries are evicted by recency. An active decoder owns
its separate encoded buffer, so cache replacement cannot invalidate its bytes.
USB buffers remain in DMA-compatible internal memory.

The existing decoded-background cache handles label/position changes without
transferring or decoding another PNG. Fit/background changes can reuse the
compressed source. Repeated assets across keys share the source cache. HA
reconnect probes existing files; ESP reboot loses the RAM cache and causes replay.
Deck-only USB reconnect restores desired images. No upload writes flash.

HA reuses its existing ESPHome services/connection and credentials. There is no
ESP HTTP upload server, extra native client, or firmware HA administrator token.
The ESP uses ESPHome's SHA256/mbedTLS adapter. Portable tests inject an independent
byte/hash oracle; the virtual host uses the already pinned Noise SHA256 library.

## Validation and remaining work

```sh
SANITIZE=1 UBSAN_OPTIONS=halt_on_error=1:print_stacktrace=1 .venv/bin/python -m unittest discover -s tests -v
.venv/bin/python tools/check_firmware.py --compile
.venv/bin/python tools/check_artwork_upload.py
npm run check --prefix frontend
npm test --prefix frontend
```

The upload checker creates fresh private `.build/artwork-upload-*` artifacts,
builds the pinned ESPHome host target, runs HA-engine tests with mocked native
actions, then tests the genuine encrypted native API in a `--network=none`
container. It uses localhost inside that container and synthetic secrets, creates
no published port, and stops/removes only its own test container. It does not
modify the existing HA lab, which is now paired to a real ESP.

Tests cover bounded/invalid input, duplicates/resume, timeouts, hash failure,
allocation failure, fifteen pinned assets under eviction, malformed PNGs,
stale renders and active USB image lifetime. Rendering still matches the pinned
upstream BMP fixture. HA tests cover optional capability discovery, no-origin
delivery, zero-transfer label edits, reconnect/replay and obsolete-layout fences.
The isolated encrypted test transfers a 20,876-byte PNG, rejects a bad hash,
resumes after API disconnect and reaches simulated USB-applied revision 2 after
a cached label/position edit, with zero HTTP downloads.

ESP SHA/PSRAM staging and USB completion now have an initial successful physical
run, followed by physical key actions and page navigation. Physical image
appearance confirmation, transfer/input latency under
load, repeated reconnects and OTA responsiveness during uploads remain pending.
Existing electrical, first-click, recovery and soak gates in
[hardware.md](hardware.md) remain pending. Native USB remains the host, logs use
UART0, and VBUS remains externally supplied and unswitched.
